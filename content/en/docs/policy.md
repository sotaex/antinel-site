# Policy and allowlists

In one line: four keys, each relaxing a different range, and one red line — a critical block is never relaxed.

## Where the policy file lives

```
<project root>/.psl/policy.json
```

A template is generated by `antinel install`. There are two ways to change it: edit it directly, or go through a command (recommended, because commands go into the audit chain automatically).

## The four keys

| Key | What it relaxes | What it does not relax |
|---|---|---|
| `whitelist.domains` | network rules only (the NET family) | sensitive surface, destructive, injection |
| `whitelist.paths` | sensitive-surface rules, and releases "writes outside the project" (DST-02) | deletion, persistence, injection |
| `whitelist.commands` | warning-level rules only | **critical is never relaxed** |
| `global_settings` | run-time settings such as `net_mode`, `alert_threshold`, `fail_closed_on_audit_loss` | the rule criteria themselves |

What the four keys have in common: **each one moves exactly one dimension**. There is no "allow everything" switch. That is deliberate.

## Three allow examples

Package installs keep warning you about a domain:

```
antinel domains add pypi.org
```

A resource folder needs to be written:

```
antinel paths add D:\demo\assets
```

A whole tree is in use (an independent project, say):

```
antinel roots add D:\demo
```

All three go into the audit chain. To undo:

```
antinel domains remove pypi.org
antinel paths remove D:\demo\assets
```

## The red line: a critical block is never relaxed

{{facts.F-002.value.critical}} rules are critical. No allowlist relaxes any of them.

The reason is direct: if a critical block could be relaxed, an allowlist becomes the switch that bypasses every rule. To let one specific block through, use `host-shield decide` and leave a record — **a recorded allow** and **a rule change** are two different things. The first can be traced. The second cannot.

## The trade-off when an audit write fails

The default is fail-open: if the write into the audit chain fails, the action is allowed, and `AUDIT_WRITE_FAILED` is printed to stderr.

To switch to fail-closed:

```
antinel settings set fail_closed_on_audit_loss true
```

After that, a full disk or wrong permissions blocks every action. The trade-off is yours. The mechanism belongs to the steward — we built both choices and do not choose for you.

## Network modes

The default is `warn`: a network command outside the allowlist is only warned about, not blocked.

```
antinel settings set net_mode block
```

After switching to block, domains that are not allowlisted get stopped. Before you switch, allow the domains you use often, or package installs and dependency pulls will fail.

To see the current mode:

```
antinel settings get net_mode
```

## Safe zones

```
antinel zone add D:\myproject
antinel zone list
```

A safe zone is "tightened by directory": writes inside the zone are controlled, and the list itself goes into the audit chain.

## See the whole policy

```
antinel settings list
antinel domains list
antinel paths list
antinel roots list
```

## Three rules for changing policy

1. **Look before you change**: run `settings list` to see the current state. Do not change it from memory.
2. **Verify after changing**: run `antinel digest --days 1` once to confirm the change took effect and did not bring unexpected blocks.
3. **Do not change the criteria**: the criteria live in `rules/default.json`. Changing them changes "what counts as a violation". To allow a specific object, use an allowlist.
