# 故障与边界

一句话：先看信号，再看边界。大多数「装了没用」都是同一件事——宿主没重启。

## 钩子不生效

按这个顺序查，别跳步：

```
antinel agent --json
antinel install --check
```

1. 看 `installed` 是不是 `true`。不是 → 重跑 `antinel install`，然后**重启宿主**。
2. 看 `host_detected` 是不是你以为的那个宿主。不是 → 用 `antinel --host <宿主> install` 显式指定。
3. `install --check` 返回 `3` → 登记与盘上不一致，重跑 `antinel install`。

三步都过还不生效，看下一条。

## 常见信号速查

| 信号 | 含义 | 动作 |
|---|---|---|
| `AUDIT_WRITE_FAILED` | 审计写失败，默认放行 | 查磁盘空间与权限；或改 fail-closed |
| `rules_integrity_fallback` | 钩子降级到回退规则集 | 重跑 `antinel install` |
| 拦截数归零但工具在动 | 宿主可能不再认退出码 2 | 跑 `python -m tools.enforce_probe`，向厂商反馈 |
| 心跳天数为 0 | 钩子没在岗 | 重启宿主 |
| `policy_changed` 落在 sidecar | 策略变更没进主链，但记录还在 | 跑 `antinel verify` 看整体 |

「拦截数归零但工具在动」是最需要警惕的一种：不是「没违规」，是「拦不住」。用执法探针区分这两件事——探针通过说明钩子有能力拦，不通过说明宿主没在调它。

## 装上但只能审计不能拦

不是故障。第一版只在 Windows 上、只在 Claude Code／ZCode／Qoder 上验证过真实拦截。其余宿主装完是审计与扫描模式，`antinel install` 会明说。

这种状态下你能用的：记账、体检、盘点、账本。不能用的：当场拦下。

## 性能

单次钩子调用时延约 {{facts.F-004.value.p50_ms}} 毫秒，其中大部分是 Python 解释器启动的开销。没有常驻进程，不扫全盘。

觉得慢，先确认是不是这个数——用 `antinel digest --days 1` 看有没有单次特别长的调用。如果是解释器启动慢（冷启动、杀毒实时扫描、网络盘上的 Python），那和我们无关，但确实会叠加。

## 审计链报错

```
antinel verify
```

报错分两种：

- **某一天的文件坏了**：那一天的记录被改过，或被截断。链会指出从哪一条起对不上。
- **缺文件**：中间有日期缺失。拷机器、清理时误删都会造成这个。

两种都不要「修一下让它变绿」——链的价值就在于它不会为了好看而说谎。留证据，重建一段新链，把断点写清楚。

## 磁盘满了

审计链有三道闸：天数、体积、剩余空间。写满之前会先清最老的日期让路，删够即停、今天不删、删了留账。

真要手动清，删整个日期文件，不要改文件内容——改内容等于篡改。

## 已知边界（再说一遍）

| 边界 | 后果 |
|---|---|
| 只匹配调用文本，不解析脚本 | 把危险操作写进 `.py`／`.sh` 再执行，拦不住，只留痕告警 |
| 不提供沙箱 | 要隔离，用容器或虚拟机 |
| 备用数据流只拦写入 | 流里的内容读不回来 |
| 不是检验检测报告 | 不具备法律效力 |
| 不能替代内核级防护 | 宿主不调钩子，钩子就不在 |

完整的诚实清单在[威胁模型与边界](/threat-model/)。

## 还是不行

带上三样东西再问：`antinel agent --json` 的输出、`antinel install --check` 的退出码、出问题那段时间的 `antinel digest --days 1`。

有这三样，问题基本能定位；没有这三样，只能靠猜。
